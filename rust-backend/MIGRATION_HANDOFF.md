# تحویل مهاجرت Zulip Gold از Python به Rust

- **تاریخ ثبت** — ۱۷ نوامبر ۲۰۲۶، تهران
- **شاخهٔ کار** — `codex/rust-backend`
- **مبنای پایتون** — `e28e86e48e`، نوک شاخهٔ `main` فورک Zulip Gold در شروع مهاجرت
- **آخرین کامیت کد تأییدشده** — `a194556392`

هدف این است که کل کد پایتون این فورک، شامل سرور، workerها، ابزارهای نصب و مدیریت، مهاجرت‌های پایگاه داده و تست‌ها، با Rust جایگزین شود. API و رفتار قابل مشاهدهٔ برنامه باید در طول مهاجرت سازگار بمانند. در توسعه، مسیر سازگاری موبایل، خواندن، افزودن و حذف واژه‌های هشدار و هر چهار عملیات متن‌های ذخیره‌شده در API و وب در سرویس HTTP مستقل Rust اجرا می‌شوند. چهار بخش دیگر منطق Rust را از داخل Django فراخوانی می‌کنند. Django مبنای مقایسه و مسیر پیش‌فرض استقرار است.

## آخرین برش

با `ZULIP_RUST_DRAFT_DELETES=1`، Rust پیش‌نویس را پس از بررسی همگام‌سازی حساب و مالکیت حذف می‌کند. مسیر وب توکن CSRF را از هدر می‌گیرد. پیش‌نویس ناموجود، متعلق به حساب دیگر یا شناسهٔ خارج از بازه پاسخ یکسان `404` دارند. یک رویداد `drafts/remove` فقط پس از commit و فقط برای مالک منتشر می‌شود. در دو حذف هم‌زمان، یکی `200` و دیگری `404` گرفت. [فعال‌سازی](README.md#delete-drafts-through-rust)

۱۸ سناریوی HTTP و HTTPS مستقیم از نظر پاسخ، مالکیت و رویداد با Django مطابقت داشتند. ۲۶ تست پیش‌نویس و ۶۸ تست بازآزمایی backend پاس شدند. یک تست وابسته به پرچم افزونه skip شد. قالب‌بندی، Clippy، ۱۳ تست Cargo و lint هدفمند پاس شدند.

در پروکسی توسعه پنج حالت مسیریابی هر کدام ۱۷ بررسی پاس داشتند و قطع upstream باعث ارسال دوبارهٔ `DELETE` نشد. در nginx ایزوله، در هر حالت ۱۵ بررسی HTTP و ۱۶ بررسی HTTPS پاس شدند. حالت‌ها مبنا، Rust برای خواندن و حذف، بازگشت فقط حذف و بازگشت کامل بودند. Tornado رویداد را فقط به مالک تحویل داد و با upstream خاموش، `DELETE` پاسخ `502` JSON و `OPTIONS` پاسخ `204` داد. [هدایت و بازگشت](README.md#route-draft-reads-and-deletion-through-proxies)

## برش قبلی خواندن پیش‌نویس‌ها

`GET` و `HEAD` پیش‌نویس‌ها در `/api/v1/drafts` و `/json/drafts` در سرویس مستقیم Rust اجرا می‌شوند. Rust تنظیم همگام‌سازی حساب را می‌سنجد و فقط پیش‌نویس‌های همان کاربر را از PostgreSQL می‌خواند. ترتیب صعودی زمان ویرایش را از رفتار فعلی Django حفظ می‌کند. توضیح ترتیب در OpenAPI با رفتار فعلی Django متفاوت است. [راه‌اندازی](README.md#read-drafts-through-rust)، [کوئری Rust](src/http/drafts.rs)

۹ سناریوی مستقیم، Basic Auth و نشست، `HEAD`، میزبان سازمان دیگر و همگام‌سازی خاموش را پوشش دادند. تست گیرندهٔ کانال، پیام دونفره و گروهی، پیام به خود و پیش‌نویس با گیرندهٔ حذف‌شده را بررسی کرد. ۲۵ تست پیش‌نویس در مبنای Django و پس از افزودن Rust پاس شدند. مجموعهٔ بازآزمایی ۶۷ تست پاس و یک تست وابسته به پرچم افزونهٔ skipشده داشت. ۱۳ تست Cargo، قالب‌بندی، Clippy و lint هدفمند نیز پاس شدند. [تست مقایسه](../zerver/tests/test_drafts.py)

## برش قبلی مسیریابی Tornado

فرمان `export_rust_tornado_routing` مقصدهای اعلان هر سازمان را از قواعد دقیق و regex در Django به فایل JSON می‌فرستد. `zulip-http` با `ZULIP_RUST_TORNADO_ROUTING_FILE` فایل را هنگام شروع می‌خواند و با همان قاعدهٔ باقی‌ماندهٔ شناسهٔ کاربر مقصد را انتخاب می‌کند. تغییر واژهٔ هشدار و متن ذخیره‌شده از این مسیر مشترک استفاده می‌کنند. اگر سازمان در فایل نباشد، درخواست پیش از تغییر داده `503` می‌گیرد. پس از تغییر سازمان‌ها یا تقسیم‌بندی، فایل را دوباره صادر و سرویس را راه‌اندازی کنید. [تنظیم مسیریابی](README.md#route-write-events-to-multiple-tornado-processes)

تست مستقیم، انتخاب صف در Django و Rust، خالی ماندن صف‌های دیگر و رد درخواست با فایل قدیمی را بررسی کرد. در staging ایزولهٔ HTTPS، دو حساب در یک سازمان از دو فرایند Tornado متفاوت رویداد متعلق به خودشان را گرفتند. ۴۲ تست backend، ۱۳ تست Cargo، Clippy و lint هدفمند پاس شدند. یک تست وابسته به پرچم افزونه در بازآزمایی skip شد.

## برش قبلی افزودن واژه‌های هشدار

با `ZULIP_RUST_ALERT_WORD_POSTS=1`، Rust افزودن واژهٔ هشدار را در API و وب انجام می‌دهد. سقف ۱۰۰ نویسه پیش از پاک‌سازی بررسی می‌شود. Rust از قواعد lowercase صادرشده از Python برای حفظ املای واژه‌های موجود و انتخاب آخرین املای تکرارها استفاده می‌کند. درج و پاک‌سازی کش پیش از commit انجام می‌شوند و سپس رویداد به همان کاربر می‌رسد. مسیر وب در POST فیزیکی توکن فرم را بر هدر مقدم می‌داند و override روش را مانند Django اجرا می‌کند. [راهنمای فعال‌سازی](README.md#add-alert-words-through-rust)

۱۹ سناریوی HTTP و ۶ سناریوی HTTPS برای POST با Django مقایسه شدند. فهرست واژه‌ها بدون فرض ترتیب مقایسه شد، چون کوئری‌ها مرتب‌سازی صریح ندارند. خرابی Memcached درج را برگرداند و تلاش دوباره پس از بازیابی موفق شد. ۴۱ تست بازآزمایی backend، ۱۱ تست Cargo، قالب‌بندی، Clippy و lint هدفمند پاس شدند. یک تست وابسته به پرچم کش افزونه در بازآزمایی skip شد.

گزینهٔ `--rust-alert-word-posts` و map آزمایشی `alert-words-write-map.conf` هدایت POST را فعال می‌کنند. بازگشت POST با حفظ خواندن و حذف Rust تأیید شد. در پروکسی توسعه، هر یک از پنج حالت ۲۴ بررسی پاس داشت. در nginx آزمایشی، ۱۱ بررسی HTTP و ۱۲ بررسی HTTPS در هر یک از چهار حالت پاس شدند و Tornado رویداد را فقط به صاحب واژه تحویل داد. خاموشی upstream در nginx پاسخ JSON `502` داد و در آزمون قطع اتصال پروکسی توسعه، upstream دقیقاً یک POST دریافت کرد. [توسعه](README.md#route-alert-word-post-through-the-development-proxy) و [nginx](README.md#stage-alert-word-post-in-nginx)

## برش قبلی هدایت DELETE واژه‌های هشدار

پروکسی توسعه با `--rust-alert-word-deletes` و nginx آزمایشی با `alert-words-delete-map.conf`، روش فیزیکی `DELETE` را در مسیر API و وب برای میزبان تأییدشده به Rust می‌فرستند. با حذف گزینهٔ توسعه یا جایگزینی map خواندنی در nginx، فقط حذف به Django برمی‌گردد. `POST` با پارامتر `method=DELETE` از مسیر Django عبور می‌کند. [فعال‌سازی و بازگشت در توسعه](README.md#route-alert-word-deletion-through-the-development-proxy) و [nginx](README.md#stage-alert-word-deletion-in-nginx)

در پروکسی توسعه، ۲۴ بررسی در هر یک از پنج حالت پاس شدند. حالت‌ها مبنای Django، خواندن و حذف روی Rust، بازگشت فقط حذف، فقط حذف روی Rust و بازگشت کامل با Rust خاموش بودند. در آزمون قطع اتصال پس از دریافت درخواست، upstream دقیقاً یک `DELETE` گرفت و پروکسی پاسخ `502` داد. lint هدفمند پاس شد و اجرای گزینه بدون پورت Rust با کد خروج `2` رد شد.

در nginx آزمایشی، ۱۱ بررسی HTTP و ۱۲ بررسی HTTPS در هر یک از چهار حالت مبنا، هدایت Rust، بازگشت فقط حذف و بازگشت کامل پاس شدند. لاگ nginx مقصد هر درخواست را تأیید کرد. PostgreSQL، Memcached و Redis آثار جانبی را تأیید کردند و یک فرایند Tornado رویداد را فقط به حساب صاحب واژه تحویل داد. با Rust خاموش و هدایت فعال، هر دو مسیر `502` با بدنهٔ JSON دادند و واژه‌ها، سهمیه و صف فعالیت و اعلان تغییر نکردند. `OPTIONS` پاسخ `204` داد.

## برش قبلی DELETE مستقیم واژه‌های هشدار

سرویس مستقیم `zulip-http` با تنظیم `ZULIP_RUST_ALERT_WORD_LOWERCASE_FILE` درخواست `DELETE /api/v1/users/me/alert_words` را با Basic Auth سرو می‌کند. مسیر `/json/users/me/alert_words` نیز با نشست Django و تنظیم طرح وب فعال می‌شود و توکن CSRF را از هدر می‌گیرد. فرمان انتشار کش می‌تواند جدول lowercase نسخهٔ Python همان استقرار را در فایل جداگانه صادر کند. Rust این جدول را در شروع می‌خواند و قواعدی مانند سیگمای پایانی و نگاشت‌های چندنویسه‌ای را اعمال می‌کند. [راهنمای راه‌اندازی و بازگشت](README.md#delete-alert-words-through-rust)

حذف روی اتصال نوشتنی اختصاصی اجرا می‌شود. پس از پاک‌سازی کش و commit، Rust رویداد `alert_words` را فقط برای همان کاربر به صف `notify_tornado` یک فرایند Tornado می‌فرستد. در خرابی Memcached، `503` برمی‌گردد، تراکنش rollback می‌شود و رویدادی منتشر نمی‌شود. اگر RabbitMQ پس از commit تحویل را تأیید نکند، داده ممکن است تغییر کرده باشد و پاسخ `503` برگردد. [پیاده‌سازی مسیر](src/http/user_reads.rs)، [تست با سرویس‌های واقعی](../zerver/tests/test_alert_words.py)

در Multipass، ۱۴ سناریوی HTTP و ۶ سناریوی HTTPS در مبنای Django و سپس با Rust مستقیم پاس شدند. وضعیت HTTP، بدنه، هدرهای منتخب، دادهٔ دو کاربر، کلیدهای دو پیشوند، رویداد و ثبت فعالیت مقایسه شدند. دو بررسی دیگر خرابی Memcached و موفقیت تلاش بعدی پس از بازیابی را روی همان فرایند Rust تأیید کردند. پروکسی توسعه و nginx هنوز `DELETE` را به Django می‌فرستند.

۴۰ تست بازآزمایی backend و ۱۱ تست معمول Cargo پاس شدند. تست وابسته به پرچم کش افزونه در مجموعهٔ بازآزمایی رد شد و هر دو تست کش افزونه با پرچم روشن جداگانه پاس شدند. آزمون اختیاری تراکنش Rust با PostgreSQL و Memcached واقعی، قالب‌بندی Rust، Clippy و lint هدفمند کد و راهنمای Rust نیز پاس شدند.

تست HTTP در Multipass اتصال مخصوص فرایند Rust را در clone پایگاه دادهٔ تست قطع کرد. نسخهٔ قبلی در هر دو درخواست بعدی `503` داد. نسخهٔ جدید همان پاسخ موفق قبل از قطع اتصال را در همان فرایند برگرداند. در آزمون جداگانه، یک نمونهٔ موقت PostgreSQL با دادهٔ نمونه کاملاً متوقف و دوباره راه‌اندازی شد. بررسی آمادگی و خواندن از `200` به `503` رفتند. پس از بازگشت PostgreSQL، هشت درخواست هم‌زمان `200` گرفتند و PostgreSQL فقط یک اتصال از همان فرایند Rust ثبت کرد. این آزمون مستقیم روی loopback انجام شد.

nginx آزمایشی با include اختیاری فقط `GET` و `HEAD` روی دو نشانی دقیق واژه‌های هشدار و میزبان مجاز را به Rust روی loopback می‌فرستد. بقیهٔ روش‌ها و میزبان‌ها از مسیر uWSGI جنگو عبور می‌کنند. برداشتن `alert-words-routes.conf` و reload، خواندن را به Django برمی‌گرداند. خطای upstream با پاسخ JSON استاندارد nginx برمی‌گردد و درخواست در Django دوباره اجرا نمی‌شود. [پیکربندی آزمایشی](staging/nginx/alert-words-routes.conf)، [راهنمای اجرا و بازگشت](README.md#stage-alert-word-reads-in-nginx)

بررسی آمادگی Rust روی `/health/rust-alert-words` از loopback در دسترس است. پیکربندی نشست، امکان خواندن جدول‌ها در PostgreSQL، پاسخ Redis و وضعیت اتصال و کانال RabbitMQ را می‌سنجد. در Multipass، قطع Redis اختصاصی تست پاسخ را از `200` به `503` رساند و با وصل شدن Redis، پاسخ دوباره `200` شد. `/health` جنگو در این فاصله `200` باقی ماند. قطع PostgreSQL و RabbitMQ در این برش جداگانه آزمایش نشد.

با Rust خاموش و هدایت فعال، بررسی Rust و هر دو خواندن واژه‌ها `502` با بدنهٔ JSON گرفتند. هر دو `OPTIONS` همچنان `204` بودند. پس از برداشتن include و reload همان فرایند nginx، هر ۱۷ بررسی با Rust خاموش پاس شدند. همین مجموعه قبل از فعال‌سازی و با هدایت فعال هم پاس شد. [تست مسیریابی](tests/check_alert_words_proxy.py)

پروکسی توسعه با `--rust-http-port 9997 --rust-alert-words` فقط `GET` و `HEAD` دو مسیر `/api/v1/users/me/alert_words` و `/json/users/me/alert_words` را به Rust می‌فرستد. شرط میزبان تطابق سازمان در مسیریابی Django و Rust است. برای بازگشت، پروکسی را بدون `--rust-alert-words` دوباره راه‌اندازی کنید. `--rust-http-port` همچنان می‌تواند برای سازگاری موبایل فعال باشد. [پروکسی توسعه](../tools/run-dev)، [دستور اجرا](README.md#route-alert-word-reads-through-the-development-proxy)

در Multipass، ۱۷ بررسی HTTP در هر یک از سه حالت پاس شدند. حالت اول گزینهٔ فعال بود. در دو حالت بازگشت، گزینه حذف شد و آزمون یک بار با Rust روشن و یک بار پس از خاموش کردن Rust اجرا شد. هدر سهمیه مقصد خواندن را مشخص کرد. تست‌ها علاوه بر پاسخ‌های خواندن، `Allow` در `OPTIONS`، اثر `POST` و `DELETE` روی پایگاه داده، رد نوشتن بدون CSRF، حفظ `POST` دارای `method=GET` در Django و مسیر یا میزبان خارج از دامنهٔ هدایت را بررسی کردند. [تست پروکسی](tests/check_alert_words_proxy.py)

`GET /json/users/me/alert_words` و `HEAD` متناظر در اجرای مستقیم Rust فعال شده‌اند. Rust کوکی نشست Django را با رکورد منقضی‌نشدهٔ PostgreSQL، امضای رکورد، backend مجاز و هش وابسته به رمز عبور فعلی بررسی می‌کند. `GET` و `HEAD` مانند Django به توکن CSRF نیاز ندارند. کوکی CSRF خراب بازسازی می‌شود و پاسخ به `Cookie` وابسته می‌ماند. در مسیر نشست، بررسی سهمیه پیش از بررسی وضعیت حساب و ثبت فعالیت انجام می‌شود. [اعتبارسنجی نشست](src/http/session.rs)، [دستور اجرا](README.md#read-alert-words-with-a-django-session)

در Multipass، ۱۶ سناریوی نشست و خواندن از نظر status، بدنه و هدرهای انتخاب‌شده برابر بودند. نتیجهٔ بازسازی کوکی CSRF از نظر قالب توکن، ویژگی‌های کوکی و بدنه یکسان بود. برای `POST` و `DELETE` بدون توکن، Django پاسخ `403` و listener خواندنی Rust پاسخ `405` دادند و واژه‌ها تغییر نکردند. تست مشترک Redis و RabbitMQ نیز چهار درخواست نشست را به‌صورت متناوب اجرا کرد و فقط دو درخواست پذیرفته‌شده به ثبت فعالیت `website` انجامیدند. [تست HTTP](../zerver/tests/test_alert_words.py)

`GET /api/v1/users/me/alert_words` و `HEAD` متناظر در `zulip-http` از PostgreSQL برای Basic Auth و خواندن واژه‌های همان کاربر استفاده می‌کنند. با تنظیم Redis، Rust همان اسکریپت Lua و کلیدهای `api_by_user` جنگو را به‌کار می‌برد و قواعد پیش‌فرض، سهمیهٔ اختصاصی کاربر و مسدودی دستی را اعمال می‌کند. با تنظیم RabbitMQ، فعالیت پس از احراز هویت و پیش از بررسی سهمیه در صف یا shard فعلی Django ثبت می‌شود. درخواست احرازشدهٔ ردشده با `429` نیز پیام فعالیت دارد. [handler](src/http/user_reads.rs)، [سهمیه](src/http/rate_limit.rs)، [فعالیت](src/http/activity.rs) و [دستور اجرا](README.md#run-the-alert-word-read-api-over-http)

در برش سهمیهٔ مشترک، Django و Rust روی دو درگاه loopback از یک clone PostgreSQL، فضای کلید Redis و vhost اختصاصی RabbitMQ استفاده کردند. هدرهای سهمیهٔ هر دو سرویس، کاهش ظرفیت با جابه‌جایی درخواست بین سرویس‌ها، بدنهٔ `429` و `Retry-After` برای سقف و مسدودی دستی بررسی شدند. هشت پیام فعالیت به shard صحیح رسیدند و worker فعلی Django افزایش دقیق شمارنده‌های هر کاربر و کلاینت را تأیید کرد. دو درخواست بدون اعتبارنامه پیام فعالیت یا هدر سهمیه تولید نکردند. مقایسهٔ ۲۰ سناریوی قبلی احراز هویت و بدنه نیز دوباره پاس شد. [تست مقایسه](../zerver/tests/test_alert_words.py)

اجرای Rust در پروکسی توسعه و nginx آزمایشی اختیاری است. میزبان‌هایی که در Rust و Django به سازمان‌های متفاوت نگاشت می‌شوند، `POST`، `DELETE` و `OPTIONS` در Django می‌مانند. مسیر نشست Rust از کلید جاری و تنظیمات متعارف کوکی و ورود استفاده می‌کند. چرخش کلید و تمدید نشست را Django انجام می‌دهد. Rust برای هش نامعتبر کوکی مرورگر را پاک می‌کند و رکورد نشست را در Django بازنویسی یا حذف نمی‌کند. بازیابی RabbitMQ و استقرار تولید برای یکپارچه‌سازی باقی‌اند. در خطای Redis یا RabbitMQ، Rust درخواست را با `503` رد می‌کند.

[موجودی مسیرهای HTTP](API_INVENTORY.md) ۱۷۱ مدخل OpenAPI را ثبت می‌کند. سه مدخل نمونهٔ مستندات‌اند و ۱۶۸ عملیات به handler ثبت‌شده نگاشت شده‌اند. موجودی همچنین ۳۹ عملیات خارج از OpenAPI زیر `/api/v1/`، ۱۳۴ مسیر `/json/` با ۱۹۰ روش صریح و ۹۶ مسیر webhook ورودی را ثبت می‌کند.

**خطاها و موارد تأییدنشده**

- در اجرای نهایی تست‌های هدفمند بالا شکست باز گزارش نشده است. دو اجرای اولیه که چند تست را در یک فرمان اجرا می‌کردند، کد خروج خطا داشتند در حالی که خود تست‌رانرها `OK` ثبت کرده بودند. اجرای دوبارهٔ مستقیم مجموعه‌های اشتراک و ذخیره‌سازی ربات با کد خروج `0` تأیید شد.
- آماده‌سازی Kiri در دانلود بسته‌های PostgreSQL به timeout و قطع اتصال خورد. مخزن PGDG در Multipass هم هنگام دریافت فهرست بسته‌ها متوقف شد. نصب PostgreSQL از مخزن Ubuntu و نصب PGroonga در همان VM مشکل عملی را برطرف کرد. علت قطعی مشکل شبکه مشخص نشده است.
- ساخت Rust در VM یک بار به علت اتصال به `index.crates.io:443` شکست خورد. همان `Cargo.lock` با `cargo vendor` روی میزبان بسته‌بندی و ساخت در VM با `--offline` تأیید شد.
- lint هدفمند Python پس از اصلاح خطاهای mypy پاس شد. بررسی `gitlint` در VM به علت checkout کم‌عمق و نبود `upstream/main` اجرا نشد. این استثنا فقط مربوط به بازبینی پیام کامیت در VM است.
- در برش ویرایش وب، lint کد، قالب‌بندی Rust، Clippy و بررسی جداگانهٔ پیام کامیت پاس شدند. lint کامل Markdown روی قالب جدول‌ها و املای شناسهٔ `github` در موجودی قبلی خطا می‌دهد.
- مقایسهٔ HTTP پاسخ‌های عادی و خطاهای مورد انتظار را پوشش می‌دهد. در مواردی مثل User-Agent موبایل Android بدون نسخه، Rust پاسخ `500` بدون قالب خطای Django می‌دهد. قبل از فعال‌سازی در تولید، قرارداد خطاهای غیرعادی، تنظیمات زبان و رفتار میزبان‌های فرعی را جداگانه بررسی کنید.
- کل مجموعهٔ backend، مرورگر و استقرار تولید روی شاخهٔ Rust اجرا نشده‌اند. جابه‌جایی ترافیک تولید، کارایی زیر بار و هم‌ارزی آپگریدهای پایگاه داده هنوز اعتبارسنجی نشده‌اند.

2. **تکمیل قرارداد مسیر خواندنی.** خواندن واژه‌های هشدار با Basic Auth یا نشست، سهمیه و فعالیت با Django مقایسه شده‌اند. هدایت و بازگشت در پروکسی توسعه و nginx آزمایشی تأیید شده‌اند. برای API متن‌های ذخیره‌شده، اجرای مستقیم، پروکسی توسعه و staging ایزولهٔ nginx تأیید شده‌اند. بسته‌بندی سرویس برای استقرار و تنظیمات میزبان، کوکی و ورود روی پیکربندی هدف باقی است. [قرارداد واژه‌های هشدار](API_INVENTORY.md#قرارداد-واژههای-هشدار)
3. **زیرساخت و استقرار مسیرها.** سیاست مشترک احراز هویت، مجوز، locale، خطای JSON، CORS/CSRF، محدودیت نرخ و ردیابی را برای مسیرهای بعدی از کد موجود استخراج کنید. بازیابی PostgreSQL پس از قطع اتصال در اجرای مستقیم تأیید شده است. بسته‌بندی سرویس Rust و Supervisor، تنظیمات staging مقصد، بازیابی RabbitMQ، تکرار آزمون PostgreSQL در staging مقصد و آزمون زیر بار باقی‌اند. [پیکربندی nginx](../puppet/zulip/files/nginx/zulip-include-frontend/app)
4. **سایر APIها و جریان‌های دارای اثر جانبی.** برای افزودن و حذف واژه‌های هشدار، HTTP مستقیم، بازگشت پروکسی و تحویل رویداد Tornado در staging ایزوله تأیید شدند. مسیریابی رویداد برای چند فرایند Tornado در staging ایزوله تأیید شده است. خواندن و حذف پیش‌نویس‌ها در HTTP مستقیم و از پشت دو پروکسی آزمایشی تأیید شدند. ایجاد و ویرایش پیش‌نویس‌ها به اعتبارسنجی گیرنده و نوشتن نیاز دارند. پشتیبانی از Memcached احرازهویت‌شده یا چندسروری در پیکربندی مقصد باقی است. ارسال و ویرایش پیام، کانال، عضویت، پیوست، جست‌وجو، ثبت رویداد و long polling، notification، webhook، worker و وظایف زمان‌دار هنوز باقی‌اند. در هر مرحله نتیجهٔ HTTP، تغییرات داده، ترتیب و محتوای رویداد، کش و رفتار retry را بررسی کنید. [قرارداد واژه‌های هشدار](API_INVENTORY.md#قرارداد-واژههای-هشدار)، [کش Django](../docs/subsystems/caching.md) و [سیستم رویداد](../docs/subsystems/events-system.md)
5. **پایگاه داده، ابزارها و حذف Python.** نصب تازه و آپگرید از نسخه‌های پشتیبانی‌شده باید با مسیر جدید همان schema و دادهٔ قابل‌استفاده را بسازند. معادل مهاجرت‌های تاریخی Django، PGroonga و جست‌وجو را قبل از حذف فایل‌های مهاجرت تأیید کنید. دستورهای مدیریت، نصب، انتشار، پشتیبان‌گیری، واردات/صادرات، analytics، billing، rendering و تست‌رانر را هم در موجودی پروژه ثبت کنید. تست‌های مرجع را پس از انتقال به fixture، تست Rust یا تست پروتکل مستقل منتقل کنید تا در پایان امکان حذف Python وجود داشته باشد. [راهنمای مهاجرت پایگاه داده](../docs/subsystems/schema-migrations.md)

برای هر برش، ابتدا baseline همان تست‌ها را روی Python ثبت کنید. سپس مسیر Rust را برای همان درخواست و داده فعال کنید، مطمئن شوید درخواست واقعاً به Rust رسیده، خروجی و آثار جانبی را مقایسه کنید و وضعیت خروج تست‌رانر را ثبت کنید. اگر اختلافی پیدا شد، مشخص کنید که مربوط به انتقال، محیط تست یا رفتار موجود است. یک کامیت قابل‌بازبینی برای هر برش نگه دارید و این سند را با شناسهٔ کامیت، حالت اجرا، تعداد تست و نتیجه به‌روز کنید. دستورهای [AGENTS.md](../AGENTS.md) و [راهنمای طراحی API](../docs/processes/api-design.md) برای هر برش اعمال می‌شوند.
